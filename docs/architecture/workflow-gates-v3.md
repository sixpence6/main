## 1. 规则目录与有效裁决

**服务端目录**是每个目标的规则来源。按目标类型与原快照确定规则 ID、检查职责、`blocking`／`advisory`、适用条件、允许证据及规则版本；模型只返回检查结果，不自行增减必审项或决定免审。实现先映射现有规则 ID，复用同一校验语义到正常执行和 S12 恢复路径。

| 检查类别 | 适用时的有效结果 | 对门禁的影响 |
|---|---|---|
| 必审 `blocking` | 每个必需规则有合法证据的 `pass` | 全部成立才可放行；缺项、`fail`、`unknown` 或无依据的 N/A 均不放行 |
| 不适用的必审规则 | 由服务端明确判为不适用，并记录原因 | 允许契约约定的省略或 `not_applicable`；模型不能反向免审适用项 |
| 已登记 `advisory` | `pass`、`fail`、`unknown` 或不适用意见 | 不改变阻断项已经满足的裁决；建议正文仍按对外内容规则处理 |
| 未知规则、非法证据或矛盾协议 | 类型化协议问题 | 停在协议校验／有界修复，不伪装为服务宕机，也不默认为通过 |

- **必审项。** S07 的确认与执行边界在提交前始终适用；两项均为 N/A、证据为空或任一项缺失都不能签发提示词批准。真实账号、确认与幂等校验继续由程序独立执行。
- **建议项。** 模型总裁决为 `pass`、所有必审项通过时，额外建议的 `fail`／`unknown` 不使协议失效。总裁决与必审证据矛盾时定位协议问题，不能无证据改写明确的安全否决。
- **风险归属。** 未经确认的卖点、权限冲突和关键证据缺失属于阻断规则；不能仅因它出现在“额外检查”中就当作审美建议。需要扩大规则目录时先版本化映射，禁止依靠任意规则名正则授予放行权。
- **覆盖。** 明确各规则是否允许多个检查实例；允许细分时每个实例都必须通过，既保留完整覆盖，又保留重复项中失败的否决作用。目标绑定、证据来源、未知规则及协议字段校验不因支持建议项而关闭。

## 2. 硬约束与软偏好

约束强度和内容是否需要审查是两条独立维度：软偏好也要保留与安全处理，审美差异却不应自动变成硬失败。

| 内容 | 默认归类 | 变更依据 |
|---|---|---|
| 商品身份、数量、准确画面文字、指定 Logo、参考用途、输出参数、用户明确必须／禁止项 | 硬约束 | 变更进入新需求版本并重新确认 |
| 一般风格、氛围、背景、配色、光影、模型提出的创意建议 | 软偏好 | 用户明确表达不可妥协要求时，在新卡片中显式升级；不从字段名自动推断 |
| 未确定事实、价格、功效、认证及授权等关键依据 | 阻塞信息／事实边界 | 补充可信来源或形成获审查的澄清；不能降为软偏好后编造 |

卡片展示“必须满足”和“偏好建议”，展开后可核对全部批准字段。确认一份卡片不等于把其中所有建议都升级为硬约束；强度、来源和用途一同进入确认摘要。用户明确指定的白底、特定布局或灯光仍可为硬约束，不能被“审美”分类静默降级。

S07 编制须表达全部确认内容，但将执行覆盖与成图硬性合格条件分开：成图只对适用硬约束逐项判定；一般风格、创意、光影等以软反馈表达，不拼入一个兜底的 `hard:composition` 来否决。软项 `unknown` 不等于商品身份、文案等硬项也可未知放行。

## 3. 完整执行快照

最终需求卡按稳定约束标识关联来源、强度与原字段，连同原有确认绑定形成不可变执行快照。背景、配色、文字布局、参考处理、保留规则与商品事实、创意、构图、光影都要有明确去向；不能靠模型在其他字段重复填写来防止丢失。

1. **合成。** 从已批准需求、创意、视觉产物合成完整快照；每个已批准的执行字段映射到快照字段或有明确理由的非执行说明。完成条件是字段映射清单无悬空项。
2. **确认。** 当前卡片、快照、revision、参考依赖与强度共同绑定摘要；内容或强度有实质变化就形成新版本。完成条件是前端展示与授权事务绑定同一快照。
3. **编制与质检。** S07 与 S09 读取同一确认快照，独立检查执行覆盖和成图合格；历史图与历史提示词始终关联原快照。完成条件是仅放在专用字段的背景／配色也可在执行请求中追溯。

既有卡片／批准缺少新字段或强度依据时，保留原版本语义；不补写历史摘要，不默许历史硬项降级。新规则作用于新需求版本，历史访问保留原快照解释，同时执行当前身份、归属、批准有效性及撤销／过期校验。规则／契约升级须有明确兼容判定，不能借恢复切换版本重新解释同一授权。

## 4. 原意图修复与状态分类

使用类型化原因而不是“覆盖值”等错误文案子串决定状态转移。将原因、是否已提交及可执行动作由服务端投影；对外呈现见前端设计第 3.3 节。

| 原因 | 后端处置 | 确认、授权与调用边界 |
|---|---|---|
| 用户需求仍缺阻塞信息 | 回 U1，在原对话集中澄清 | 实质补充形成新版本；不提前生图 |
| 文本格式／覆盖映射等可修复编制错误 | 绑定原快照，预算内定向修复，再独立审查 | 只修文本候选；确认未变、可证明尚未提交时沿用原意图，不另计生成次数 |
| 已证实的实质需求漂移／未经确认的新卖点或文字／硬项弱化 | 隔离候选，回 U1 重新核对需求 | 原授权不覆盖新内容；明确否决或危险偏差不走自动修订，不能以反复抽样刷通过 |
| 适用硬项明确失败或安全拒绝 | 保留隔离与已批准的安全说明 | 不自动重生成图片，不通过重复抽样刷通过 |
| 关键证据不足／硬项未知 | 保留待核实／内容未放行状态 | 补证或执行实际可用的恢复动作，未知不推导通过 |
| 契约错误与技术故障 | 分别记录校验原因或适配器故障，保留检查点 | 技术故障自动重试为零；刷新、重新登录与重启均不发起调用 |
| 远端受理／结果未知 | 优先只读核实原结果，保守保留任务事实 | 超时不等于未提交；不同新任务仍需风险确认、额度与单项目检查 |

**有界修复。** 文字候选预算读取 SRS 第 12 节；修复前后都记录候选、次数和规则版本，刷新／恢复不重置预算。只有可修复格式或非危险业务偏差可在当前连续执行中按预算修订；技术中断之后继续调用模型须走明确的手动恢复。无法证明尚未提交或原授权有效时停止文本修复后的自动推进。

**覆盖与语义。** 多句要求在提示词原样出现时，分号、句号或换行不应造成漏覆盖；语序／连接词变化需有可解释的覆盖与独立语义检查。准确画面文字、数值、否定、数量和来源边界保持原义，禁止用跨无关语句拼字或字词子序列替代语义合格。未覆盖内容先判编制问题，不直接声明用户已改变需求。

**计数。** 原意图下文本候选修复、只读核实、获授权的恢复与幂等重放不新增生成次数；既有受理计数不因失败退回，槽位依真实终态结算。图片已经提交或提交事实未知时，不存在“修文本顺便重新提交”的旁路。

## 5. 工作流与前端交接

用户可见主链：

```text
账号／输入／范围 → 必要时识图 → 需求、创意与视觉整合
  → 最终需求审查 → 原对话确认并受理 → 提示词编制与执行审查
  → 生图 → 成图质检与独立审查 → 交付清单审查与原子发布
```

此链路是现有职责的用户投影，不是删除中间审查的授权。G00—G08 继续存在：业务产物的批准、最终卡片批准、用户确认、提示词批准、质检报告批准、图片批准和交付／访问条件各有归属；报告准确描述失败可以获批，但不代表图片已合格。

正常调用与 S12 恢复使用相同规则目录、约束分层及快照校验；已存在的批准只能在目标摘要、依赖、规则／契约版本和有效性均匹配时复用。变化时按既有撤销／过期规则处理，不能把旧批准移植到新目标，也不能通过“合并审查”提前展示未批准候选。

前端保持共壳、单聊天主体、原输入框和只读成果子路由。可修复编制不让用户无理由重复确认；真实需求变化才经原输入框回 U1。未发布／硬项未知仍停留 U2 的任务状态，不进入 U3，也不因审核员意见直接显示图片。具体文案、操作和卡片行为只在前端设计维护。

**合并审查是后续候选。** 保留当前逐角色独立交接。若后续减少重复调用，另行列出移除点、替代校验、对外可见时机、证据覆盖与调用对照，完成明确的设计批准及对应验收后才替换；本次没有批准删除识图、提示词、成图或交付的独立审查。

## 6. 实施顺序与结束条件

按 HLD 的 R1 → R2 → R3 串行门槛推进，以下是同一阶段内的修复依赖，不新开一条可绕过前置验收的发布路径。已有阶段发现回归时先补证／修复相关门槛。

| 次序 | 主责与变更边界 | 进入下一步的条件 |
|---|---|---|
| A 规则一致性 | R1 内容边界；R2 正常／恢复调用接入同一判定 | 适用必审项不能 N/A 免审，合法建议不误拦，未知协议安全失败 |
| B 原意图修复 | R2 提示词、恢复、受理账本与调用归因 | 原快照未变的修复不新增授权／计数；技术失败、远端未知不重发 |
| C 快照与强度 | R2 需求合成、提示词与成图；回归 R1 出口 | 全字段可追溯，软硬项对照正确，历史快照不改写 |
| D 聊天呈现 | R3 消息／任务卡、返回修改与成果路由 | 安全原因与动作来自服务端，同任务卡更新，导航与跨账号回归通过 |
| E 发布复验 | 各阶段；Release 实际运行环境 | 第 8 节全量有证据，旧权限／额度／发布门槛无回归 |

先加能复现对应问题的回归，再改实现；用例验证真实工作流入口、临时 SQLite、适配器调用次数及资源可见性。私有 helper 探针用于定位，不能单独替代集成验收。业务代码、测试和证据分别按仓库目录约定放置，本文不新增通用工作流框架或授权引擎。
