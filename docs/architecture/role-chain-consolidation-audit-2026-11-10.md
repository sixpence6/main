## 当前链路

[role_graph.py:14](../../main/backend/app/workflow/role_graph.py#L14) 定义四个对外 persona：外观、策划、制图、交付；[contracts.py:260](../../main/backend/app/workflow/contracts.py#L260) 注册八个活动工序。

| 内部角色 | 阶段与职责 | 建议 |
| --- | --- | --- |
| intent_router | S01，请求范围与动作分类 | 并入需求助手 |
| conversation_router | 消息归因：闲聊、补充、需求/提示词修改等 | 与意图分类统一，明确动作优先程序处理 |
| reference_analyst | S02，可选参考图观察 | 保留按需识图与独立来源证据 |
| requirements_consultant | S03，需求整理与澄清 | 唯一需求状态写入入口 |
| creative_planner | S04，一个创意方向、卖点、文案 | 与视觉导演一次产出 |
| visual_director | S05，构图、光影、色彩、背景、文字布局 | 合并为视觉策划 |
| generation_engineer | S07，把已确认快照编译为执行提示词 | 独立保留 |
| delivery_manager | S10，文件名提示与交付说明 | 默认程序生成清单 |

`run_role` 每次执行都会发起独立请求。多个工序使用同一 persona，不等于合并调用或共享状态。当前默认 `WORKFLOW_GATE_MODE=off`（[config.py:89](../../main/backend/app/config.py#L89)）；output_reviewer、quality_compliance 在历史兼容注册表，默认新流程跳过它们的模型调用。各阶段仍有非默认配置/兼容分支，不应按默认主链重复计算这些调用，也不能声称所有旧角色引用都已删去。

```text
S01 请求路由
 → S03 需求整理/澄清
 → S04 创意方向
 → S05 视觉方案 + 程序组装最终需求卡
 → S06 用户确认需求
 → S07 提示词编译
 → S08 用户确认最终提示词
 → S09 程序生图与技术校验
 → S10 交付清单 + 用户发布确认
```

无参考图、无澄清/修订/失败恢复的完整默认主链，静态计数为 6 次模型调用；有参考图通常另加 1 次。图片供应商调用不计入此处，S05 的程序组卡也不算额外模型调用。消息修改等情形会增加调用。

## 建议的实际合并

| 目标 | 吸收的工序 | 输出 |
| --- | --- | --- |
| 需求助手 | intent_router + conversation_router + requirements_consultant | 统一意图、需求 delta、澄清问题，程序管理唯一有效状态 |
| 视觉策划 | creative_planner + visual_director | 一次产出创意和完整视觉方案，程序生成用户确认卡 |
| 提示词编译 | generation_engineer | 已确认快照对应的执行提示词和覆盖映射 |
| 按需识图 | reference_analyst | 带原图来源的直接观察，不能混入创作假设 |
| 程序交付 | delivery_manager 默认职责 | 从图片批准、文件事实和模板生成清单，保留发布确认 |

```text
用户 → 需求助手（可选识图，按实际未知项澄清）
     → 视觉策划 → 用户确认需求
     → 提示词编译 → 用户确认提示词
     → 程序生图/校验/准备交付 → 用户确认发布
```

按前述计数条件，无参考图由 6 次降为 3 次，有图由通常 7 次降为 4 次。这是调用次数估算；未实测耗时、token 成本或成图质量，不能声称延迟/成本同比减半。

S04 与 S05 都在需求确认前，使用同一批需求与来源，一个创意方向和视觉落地可以在一次结构化输出中表达。合并必须减少实际 run_role 次数，不能只换 persona 名称。依据：[s04.py:674](../../main/backend/app/workflow/stages/s04.py#L674)、[s05.py:794](../../main/backend/app/workflow/stages/s05.py#L794)。

当前 [DeliveryData](../../main/backend/app/workflow/contracts.py#L205) 只有 asset_id、版本、filename_hint、caption；前两项是精确事实，后两项默认可用确定模板。移除默认 [s10.py:499](../../main/backend/app/workflow/stages/s10.py#L499) 的模型依赖，可避免已完成图片卡在清单生成。未来若需要自由交付文案，再按需调用。

保留提示词编译：视觉方案要先由用户确认，执行提示词才能绑定确认快照。把视觉与编译改成同一角色名，仍需跨用户确认分成两次调用，不能省略停点。S06、S08 和发布确认，以及去重、额度、快照、文件校验与恢复由程序继续管理。

## 实施顺序与验收

1. 先修需求状态：模型返回 delta，程序区分未修改、明确设值、明确清空、未知与冲突。null/空数组不能一律解释为删除；只更新被用户修改的字段，记录字段来源与回答/确认状态，报告与下轮输入读取同一权威状态。
2. 结构化澄清：稳定问题 ID、字段目标、选项 ID、选项值和补充要求共用一个数据源。“其他，请给原文”保持待补充；无选项题只展示自然语言示例。失配简码只追问失配处，不清空已有结论。
3. 程序化交付；再合并 S04/S05；最后统一两个路由与需求助手，明确可由程序直接处理的确认/回答/状态动作。
4. 同步 DAG、契约、提示词、动作推进和模型计数测试；给旧产物及 S12 已持久化检查点保留兼容恢复路径。按既有 HLD 阶段验收推进，不把设计文档视为上线证据。

验收至少覆盖：本报告探针转绿；简码与自然语言等价；尺寸变化不丢主体/风格/无文字结论；显式清空和冲突可表达；参考图变化只更新依赖项；无参考图正常完整流程 3 次模型调用；两次用户确认与发布确认均保留；刷新/恢复不重复生成。
