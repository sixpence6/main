## 1. 产品目标与当前基线

目标用户不需要学会提示词或美术术语，也能通过表达用途、挑选方向、指出不喜欢的地方，逐步得到接近自己想法的电商图片。助手承担提炼目标、提出设计建议、解释选择和累计偏好的工作。

建议将产品定位表述为：**一个会带着用户想清楚、选方向、做图片、再调整的创作助手。**

当前工作区的可核查基线：

- `main/backend/app/workflow/prompts.py` 的 DIRECT_BASE / DIRECT_ROLES 强调“主体已知就 ready”，用途、风格、构图等可采用默认。
- `main/backend/app/workflow/collaboration.py` 的 accept_requirements 会过滤多数用途与美术偏好问题，并在无问题时填入商品展示、自然摄影、主体居中等默认值，继续视觉规划。
- `main/backend/app/workflow/contracts.py` 已定义 BriefData、RequirementUpdate、ClarificationQuestion；单个问题支持最多三个选项。
- `main/backend/app/workflow/requirements.py` 已提供需求累计、来源记录、问题和答案保存，以及编号答案解析；这些能力可作为扩展起点，但不代表已实现本规划的交互规则。
- `main/src/pages/ChatPage.vue` 与 `main/src/composables/useChatFlow.ts` 承载当前聊天、输入、任务状态和自动继续逻辑。
- 当前四角色协作修订已移除逐阶段业务确认。本文建议增加用户需要的探索交流，允许自动准备提示词，不恢复固定需求表单或逐阶段审批；图片执行前必须确认可编辑提示词。

当前不足：知道“画什么”就进入制作，尚不能充分代表已经理解“这张图要解决什么问题、用户喜欢什么”。但一律增加问答也会拖慢已经说清需求的人，因此需要按意图和不确定性选择交互。

本规划与 HLD、前端设计、工作流文档中 2026-11-10 的当前修订衔接；现行提示词确认要求以本页顶部失败验收修订为准；旧逐阶段需求审批仍仅作历史追溯。本文不作为发布或最终用户验收证据。

## 2. 总体体验：按需引导，随时委托

不要求用户先选择“新手/专业模式”。通过当前输入决定下一步，并允许用户随时说“你来定”“直接做”“先讨论一下”。

| 用户输入或上下文 | 推荐行为 | 图片提交时机 |
| --- | --- | --- |
| “帮我做一张钢笔宣传图，看着高级一点” | 简短复述，先澄清用途或一个关键方向 | 关键方向得到回答或用户明确委托后展示提示词，确认后生成 |
| 已给用途、主体、画面方向和限制 | 简短说明理解并制作 | 无额外探索轮次；展示提示词，用户确认后生成 |
| “我也不知道，你帮我选吧” | 给出推荐及一句原因；已知主体时采用可修改的设计默认 | 已有生图请求则准备提示词等待确认；纯咨询时先讨论 |
| “这两种风格有什么区别”“先别生成” | 解释差异、帮助选择 | 不提交图片请求 |
| “保留产品，背景再干净一点” | 继承原需求，仅更新背景方向 | 已明确要求改图则准备新版本提示词，确认后生成 |
| “不好看”“没那个感觉” | 先帮助定位一个主要问题 | 未明确要再生成时不自动消耗新一轮 |

核心循环：理解目标 → 提供少量方向 → 累计选择 → 简短复述 → 展示并编辑提示词 → 点击确认生成 → 帮助指出偏差 → 定向修改。

这是一组可跳过、可返回的对话动作，不是所有用户都必须走完的固定流程。

## 3. 六项核心互动机制

### 3.1 从用途切入，而不是让用户描述完整画面

优先问用户知道的事情：这张图片在哪里用、希望别人看完有什么感受、主要想突出什么。先利用已提供的信息，不逐项询问。

例如：

> 这张钢笔图主要是让买家看清产品，还是突出送礼的感觉？也可以让我按商品展示来安排。

用途影响画面方向时优先问用途；参考图身份不明时先问图片作用；画面方向已明确时可直接跳过。平台用途不自动改变系统支持的输出尺寸，不能暗示已经支持任意比例。

### 3.2 将模糊感受翻译成可比较的方向

用户说“高级一点”，助手提出具体解释供选择，不把自己的理解当成用户事实。

> 你说的高级，我先给两个方向：
> A. 干净克制：浅色背景，商品细节清楚。
> B. 商务稳重：深色背景，灯光集中在产品上。
> C. 你帮我选。

默认推荐两个差异清楚的方向，第三个选项可用于委托助手。自由输入始终保留，不要求用户凑选项。每个方向说明“画面会有什么差别”，少用“电影感、体积光、三分构图”等术语；用户主动使用专业语言时再匹配其表达。

“你来定”的范围必须与本轮问题绑定：选背景的委托不代表可以改变商品或添加卖点。用户说“都不喜欢”时改变方向轴，不反复改写同一组选项。

### 3.3 渐进追问与问题预算

建议默认每轮一个主问题；两个紧密相关且回答简单的问题才可同轮出现。探索性问题建议最多三轮，作为初始产品参数，不是现行规格或研究结论。

提问前检查：

1. 用户是否已经回答，能否从当前图片或本轮明确指代中获得答案？
2. 不同答案是否会明显改变用途、主体呈现或主要画面方向？
3. 这是否必须由用户决定，还是可以解释后采用设计默认？

优先处理商品身份、参考图用途、明确文字原文、相互矛盾的硬要求；再处理用途和一个主要审美方向。光线、背景细节等由助手承担，除非用户特别关心。

达到探索预算后：总结已知内容并推荐默认方向。已有明确制图请求时沿该请求继续；纯讨论时停在建议。商品身份仍不明、明确要求的文字仍缺原文、硬要求仍矛盾时不能靠预算耗尽自动补全。

用户选择“不知道”后应推荐并说明原因，不重复抛出同一个问题。用户一次回答多项时全部累计，下一轮只处理仍有必要的问题。

### 3.4 用简短复述帮助纠偏

对齐到足以制作时，用两三句话描述计划，让用户知道实际采用了什么：

> 我会按商务礼品方向做：钢笔保持参考图里的样子，背景深一些，让产品更突出。先不加文字，避免画面太满。

复述应区分“用户说的”和“我建议的”，只突出本次关键选择。没有待决问题且已有生图请求时，复述后继续生成，不再要求回复“确认”。还有开放选项时必须等答案，不能一边询问一边提交图片。

用户可说“别用深色”“文字还是加上”等自然语言修正。修改使旧问题或旧方案失效时，保留历史供回看，但不允许旧选项覆盖最新版本。

### 3.5 参考图用于降低表达负担

有图时先区分图片角色：是实际商品、只借鉴布局，还是只参考氛围。清楚的上传说明直接复用；角色不明且会影响商品身份时才问。

对图片描述使用可核查的表达，例如“我看到笔身偏深色、笔夹有反光”。无法看清的材质、品牌、性能和尺寸不写成事实。

建议后续增加轻量方向示意：用简单布局图、已有合适示例或色块说明主体大小、留白、背景和文字区域。注明“构图示意”，不让用户误认为是自己的生成结果。示意优先不调用付费生图；需要生成新样图时清楚说明会产生一次新生成，并等待对应生成意图。

用户可以说“保留这张的干净感觉，产品换成我的”，助手拆解为保留的设计特征与替换的主体，不整张照搬。

### 3.6 出图后帮助用户说清不满意

图片后提供一句有针对性的引导，例如：

> 如果想继续调整，可以告诉我产品不够突出、背景太复杂，还是整体感觉不对。

用户说“太乱了”时，先提出可理解的修改建议：减少道具、拉开留白、减少文字。说“B，但别那么暗”时同时继承 B 的主方向并调整亮度，不当成相互矛盾的两个回答。

用户已经明确说“去掉文字重新做”时直接准备修改后的提示词，等待用户确认再执行；只说“不好看”时先判断是哪类偏差。每次修改保留未改变的商品、文字和限制，简短交代本轮变化。不承诺当前图片接口尚未证明支持的局部无损编辑。

## 4. 一段目标对话

用户：帮我做张钢笔的宣传图，要高级一点。（附商品图）

助手：我看到你上传的钢笔了。这张图主要想让买家看清产品，还是突出商务送礼的感觉？也可以让我来选。

用户：送礼用。

助手：那我建议走稳重一点的方向。你更喜欢 A. 深色背景、产品突出，还是 B. 浅色桌面、自然精致？也可以让我选。

用户：A，但别太暗，不要文字。

助手：我会保留钢笔原来的样子，用偏深但能看清细节的背景，突出商务送礼感，不加文字。接下来整理提示词给你检查。

助手：（展示完整提示词及可编辑文本框、输出尺寸与参考信息）你可以直接修改提示词，点击“确认使用以上提示词生成”后才会生图。

用户：（可选修改文本）点击“确认使用以上提示词生成”。

助手：（展示生成结果）如果觉得离想法还有一点差别，可以告诉我产品不够突出，还是背景感觉不对。

用户：背景太抢眼了，简单点重新做。

助手：这次减少背景装饰，让钢笔更突出；送礼方向和不加文字保持不变。下面是更新后的提示词，你可以修改，确认后再生成。

说明：是否能忠实保持商品外观取决于当前图片能力，助手表达设计目标，不宣称已实现像素级保持。示例里的用途和风格均为对话选择，不自动添加未提供的商品性能或宣传文案。

## 5. 实现设计与现有代码衔接

继续使用需求助手、参考图分析师、视觉策划师、生成工程师四个角色。需求助手主持交流，视觉策划师提供方向建议，其他角色接收累计后的需求。不增加一个向用户重复询问的独立“审核角色”。

### 5.1 对话决策与图片执行分开

在现有需求状态上增加一个可持久化的交互决策层，逻辑上区分：探索目标、选择方向、等待关键补充、可以制作、结果反馈。实现时映射到现有阶段与 needs_input 机制，不并行维护另一套工作流阶段真相。

建议的内部字段：

| 数据 | 用途 |
| --- | --- |
| 当前生成意图及其来源消息 | 区分讨论、已请求制图、用户暂缓，决定是否可以提交 |
| 当前需求版本与字段来源 | 区分用户明确、图片观察、助手建议、用户委托、未知、冲突 |
| 当前唯一主问题、选项与目标字段 | 让按钮、字母答案和自然语言回答有同一绑定 |
| question_id、option_id、requirement_revision、message_id | 防止过期选项、刷新和并发覆盖最新需求 |
| 探索轮数与已回答主题 | 控制负担，避免换措辞重复询问 |
| 最新方向建议及选择状态 | 未被采用的方案不进入实际生成快照 |
| 改图目标与本次变更 | 继承未修改内容，并将反馈指向正确图片版本 |

模型负责提出回复、问题和方向；程序负责问题版本、来源绑定、生成意图、幂等与图片提交条件。不能只改提示词，因为当前 collaboration.py 仍会过滤美术与用途问题并自动继续。

设计默认只能补审美安排，不能补商品材质、品牌、规格、功效或保证性卖点。已读图像信息应保留其不确定性；用户未纠正不等于已确认。

### 5.2 前端表现

- 保留现有消息流与唯一输入框，在相关助手消息下内联展示少量选项按钮；不另起需求面板或第二个输入入口。
- 点击选项发送与文字回答等价的领域动作，携带问题和版本标识，并展示可回看的用户选择记录；按钮不能直接绕过服务端决定触发生图。
- 同时支持自然语言、“A”“1A 2B”等原有回答习惯；无明确待答问题的孤立字母不随意匹配历史问题。
- 选项可键盘操作，有文字标签；小屏正常换行，不只靠颜色区分；选择后及时显示已选和等待状态。
- 历史问题可阅读，只有当前版本的待答问题可操作。刷新、切换会话后从服务端恢复同一待答状态，不自动生成新任务。
- 首版仅文本与选项。示意图后置，避免首期同时承担图库、样图生成和新媒体协议。

### 5.4 必须覆盖的边界

- 生成中收到新意见：保存为后续修改意图；不静默改写已提交快照，也不自动并行再发一张。
- 远端结果未知时：沿用现有查询与恢复机制；继续聊天不能触发重复提交。
- 多图或多个历史版本的“这张”：目标不明确时问一次指代，不猜图。
- 已选 A 后更换商品图：保留与商品无关的用户偏好，重新核对依赖旧图的观察与保留要求。
- 用户反悔、返回上一步或说“先别做”：更新生成意图；已提交任务只如实报告状态，不声称必然可撤销远端执行。
- 老会话与旧任务：字段缺省有兼容策略，问题快照与图片执行快照版本明确，旧流程不会被新选择错误唤起。

## 6. 分期与验收

各期作为现有 v3 串行阶段内的增量，不改变 R1 → R2 → R3 及其前置验收约束。以下周期先后是依赖顺序，未评估实际人力，不承诺日历工期。

### P0：让模糊需求能对齐，清晰需求仍能直达

范围：按需引导决策、每轮主问题、最多三个选项、委托默认、需求累计、简短复述、生成意图与版本校验、文本选项界面、可编辑提示词与显式确认、刷新恢复。

完成条件：

1. “钢笔宣传图，高级一点”在主体明确后仍能得到有意义的用途/方向引导，不立即套居中默认生成。
2. 只问会改变方向的问题；用户说“你来定”后不重复追问可默认的审美项。
3. 已给清晰需求或明确委托设计时，额外探索轮次为零，但必须展示可编辑提示词并等待确认。
4. 自由文本、字母答案、按钮答案写入同一需求来源；“A，但别太暗”两部分均保留。
5. 没有待决问题且有制作请求时准备提示词；用户确认当前提示词前图片提交为零，存在待决问题或“先讨论”时也为零。
6. 重复点击、刷新和过期选项不重复提交，不覆盖新版本；恢复当前对话后待答问题一致。
7. 已知字段不因缺省、换问法或重新识图被整体清空；参考图事实和设计建议有区分。
8. 修改提示词后，实际供应商请求与历史提示词使用用户确认的文本；保存失败、空白正向、旧快照和暂停不得提交。

### P1：让“不满意”能变成明确修改

范围：结果后的定向反馈、不满意归因、保留项继承、参考图用途交流、修改目标绑定。

完成条件：对“太乱了”“不够高级”“产品太小”“只换背景”等用例，能提出一个主要修改方向或执行明确修改；不擅自重写商品、文案和用户禁止项。无法支持局部编辑时如实按当前能力重新生成。

### P2：用可视化进一步降低选择难度

范围：构图示意与色调方向、可解释的偏好记忆、多次调整后的偏好摘要。

完成条件：示意与实际结果易于区分；新的生图调用来源清楚；长期偏好可查看、修改和清除，单次项目选择不会默认升级成跨项目偏好。

建议先交付 P0，再根据真实用户任务验证决定 P1/P2 的优先细节。先验证追问是否帮助用户选方向，再投入样图库和长期偏好系统。

## 7. 如何判断做得更好

不能只看问题变多、对话变长或生成更快。建议进行小规模可用性观察：招募约 5—8 位目标用户，各完成一个模糊想法任务和一个已有明确要求的任务。人数是本次建议，不作统计显著性承诺。

| 指标 | 看什么 | 使用限制 |
| --- | --- | --- |
| 从模糊想法到愿意制作的比例 | 引导是否帮助用户作决定 | 有些用户只是咨询，应单独归类 |
| 首次结果的用户主观符合度 | 结果是否接近期待 | 用用户评价，不能仅用模型自评分 |
| 探索轮数与退出位置 | 是否问太多、哪里卡住 | 更短不必然更好，按任务清晰度分组 |
| 重复提问与明确要求丢失 | 上下文累计是否可靠 | 记录可审查的具体实例 |
| 首次生成后的修改原因 | 主要是理解偏差还是画面质量 | 二者分开归因 |
| 无意生图与重复提交 | 讨论和选择是否误触发执行 | 可复现的违规案例视为验收失败 |

首期建议底线：明确需求不被强制拉长、待答时不提交、旧选择不覆盖新需求、明确要求不丢失。探索最多三轮、每轮一个主问题等参数可在观察后调整，变更时同步规范与验收。
