# v3 最值得实施的架构改造方案

状态：**待选择的架构提案，不是已采纳 ADR，也不是实现授权或 v3 验收结果。**  
评审日期：2026-10-31（Asia/Shanghai）。源码基线：`integration/v2`，`99c3fcd`，包含评审时已有未提交变更。  
规范入口：[SRS v3](../../vesion/v3/SRS_v3.md)。源码依据、测试范围和外部核验见 [证据索引](v3-refactor-evidence.md)。本文只定职责方向、迁移顺序和验收门槛，不提前冻结新 interface 的方法、路由、表结构。

## 结论

**保留现有单体、SQLite、Vue 和 v2 审查流程，先深化项目访问 module，再深化生成受理 module，最后收拢账号上下文内的工作台投影。**

v3 的主要风险是身份、单次授权和状态解释散落在多个调用者，而不是文件数量。单独接登录页、调整 semaphore 数值或把四页拼成一页，都不能建立这些保证。

| 顺序 | 候选 | 推荐强度 | 为什么现在做 | 证据 |
|---|---|---|---|---|
| R1 | 项目访问：身份、归属、内容门禁有序组合 | **Strong** | 所有业务读取、写入、资源字节和 R2 都依赖它；漏一个出口就破坏个人工作区 | E1—E3 |
| R2 | 生成受理：确认、意图、幂等、计数、槽位、恢复事实集中 | **Strong** | v3 把受理提前到提示词编制前，现有 S08 创建任务的时机不匹配 | E4—E6 |
| R3 | 工作台：账号生命周期内的三状态投影 | **Strong** | 切号隔离、当前修订与历史预览需要统一解释，不能沿用旧四阶段导航判定 | E7—E9 |

**第一项选 R1。** R2 的一次授权必须有可信操作者和本人项目；R3 的浏览器隔离不能代替后端保护。数据来源核验与备份是三项之前的安全前置，不作为另一个抽象化改造项目。

## 如何使用本文

- 选择候选时，读对应 R 节及证据 E 节；进入实现前，先确认该候选及其 interface 设计，再按 P0—P5 顺序推进。
- 修改账号、项目、资源出口时读取 SRS 第 2—7 节；修改生成时读取第 9—10 节及继承的 v2 门禁；修改工作台时读取第 5、8 节；迁移或恢复时读取第 11—12 节。
- 产品参数只从 SRS 第 12 节读取；prompt pack、内容审批契约与既有尺寸修订沿用 SRS 指向的权威来源。本文不复制它们。
- 每个阶段以“完成条件”结束。缺证据保持未完成；发现来源冲突、归属不明或安全假设不成立时，停止对应动作并记录需要确认的差异。

## R1：深化项目访问 module

### 问题与改造方向

现有 `Project` 无所有者字段，`require_project` 只检查存在性；列表、直接生成记录读取、工作流动作和图片字节分别进入自己的路径。现有 `workflow/access.py` 有真实内容门禁 depth，但并不认证账号或确认所有权。它在单用户基线中有价值，不能被当成完整的多账号保护（E1—E3）。

**方向：把“已验证身份访问本人项目”集中起来，复用内容门禁，而不是让每个调用者补一套用户判断。** 账号、密码与会话是 v3 必需的新 implementation；既有项目读取／操作是本候选要深化的 module。两者各自维护自己的状态，不把密码逻辑塞进内容审查。

- **职责与 seam：**身份核验之后、业务对象装载及返回之前是项目访问 seam；子对象从可信项目关系解析归属，后台动作同样使用这套规则。当前阶段只明确职责，不指定新 interface 的形状。
- **implementation：**集合查询先按主体过滤，再排序、分页、计数；直接 ID 读取先确认所属项目再暴露元数据；修改时在对应事务内重验账号状态、归属和对象关联。管理员作为创作者无跳过归属的分支。
- **内容组合：**本人可访问身份成立后，继续运行批准、撤销、过期、摘要和发布检查；归属认领不批准旧内容。最终文件路径仅从已核验对象解析，字节出口也执行同样顺序。
- **adapter：**保留 HTTP 入口与受控后台调用；持久化直接使用现有 SQLite implementation。只有一个存储选择时，不为“以后换库”引入通用 Repository 或授权引擎 adapter。
- **depth / locality / leverage：**调用者不再同时掌握身份、所有者关系和错误收敛；所有出口共享这些保证，A/B 账号与管理员用同一个 interface 测行为。
- **deletion test：**删除当前仅查存在性的 `require_project` 只会搬走少量代码；删除深化后的 module，应使身份／归属／关联校验重新散落到各调用者。若调用者仍手写这些规则，新 module 仍然 shallow。

**文件范围：**`main/backend/app/models.py`、`routers/*.py`、`services/projects.py`、`workflow/access.py`、`presenters.py`，以及新增的账号／会话实现与迁移。已有内容门禁继续保留，不按“缩短文件”重写。

**验收：**权限矩阵逐组合验证；同账号本人待审对象与他人对象区别正确；匿名业务访问拒绝，非管理员管理操作拒绝，已认证访问他人／不存在对象统一不可获得；列表、游标、详情、工作流、恢复、预览、下载及实际字节均覆盖。对应 `V3-AC-01—21、33—34、39—40` 中相关条款。

## R2：深化生成受理 module

### 问题与改造方向

现状是 S06 保存卡片确认，S07 编制并审查提示词，S08 才创建 `Generation` / `GenerationJob`。S08 的请求身份依赖尚未在确认时产生的提示词产物；它可承担执行幂等，但不能直接代表 v3 最初的一次授权。只在 S08 加次数检查，会让受理后的提示词失败无法按 v3 记录一次受理（E4—E6）。

**方向：在同一次明确确认操作中，先核验最终卡片，再原子受理一个稳定意图；S07、S08 和恢复消费这个意图。**

- **职责与 seam：**受理 seam 放在“S06 等价确认动作 → S07 编制”交接处，既不在确认之前，也不等到生图调用之前；HTTP 动作、后台推进与恢复围绕同一意图关联。
- **implementation：**短事务内核验账号、项目、卡片／参考／尺寸快照、稳定请求标识、额度和槽位，原子保存本次确认、授权、意图与计数／占用。事务提交失败没有受理；成功后才允许提示词等外部调用，网络等待不占写事务。
- **幂等：**在身份与归属成立后识别原意图；相同标识和相同参数返回原记录，不因额度随后耗尽而另计；同标识不同参数拒绝。用户受理身份与提示词产物／执行尝试身份分开。
- **执行与恢复：**明确区分已受理、执行尝试、远端结果未知和内容已发布；普通超时、重启或页面恢复不推导为远端未受理，不自动释放未知占用、退计数或重发。恢复原任务／找回原结果不另计，明确风险确认的新任务才新受理。
- **长任务：**授权与所有者持久化；退出或会话过期不撤销原任务。每次新增模型调用和发布前检查账号仍可执行；禁用后的返回内容安全隔离，恢复账号不自动续发。
- **adapter：**沿用现有真实供应商 adapter 与测试 stub；用真实临时 SQLite 验证事务与竞争，不增加通用调度 adapter 或消息队列。`ProjectLocks` / semaphore 只保留为进程内协作手段，持久化意图及槽位才是受理事实。
- **depth / locality / leverage：**interface 背后集中一次授权、计数和恢复结算，正常提交、重复点击、提示词失败、找回与重启共用同一组不变量。
- **deletion test：**删除深化后的 module，额度和授权规则必须重新出现在确认、执行、恢复、找回调用者；若只是把 `_submit` 改名转发，没有产生 depth。

**文件范围：**`workflow/stages/s06.py`、`s07.py`、`s08.py`、`s11*.py`、`workflow/state.py`、`workflow/tables.py`、`services/generations.py`、`services/recovery.py`、`db.py` 及新增受理记录迁移。保留独立审查、不可变快照、G00—G08、原子发布与单项目活跃限制。

**验收：**受理事务的每个写入点注入故障；不同连接同时竞争用户／实例／项目槽位；双击、丢响应与跨标签重放只有一个意图、一次计数、应用侧至多一次原生图提交；提示词失败仍留原意图；未知、找回与崩溃恢复无自动重发。对应 `V3-AC-19、24—32、37`。

## R3：深化账号上下文内的工作台 module

### 问题与改造方向

`useWorkspace` 暴露大范围状态，`WorkflowPanel` 另行推导确认、动作与批准；旧默认导航会因存在历史成功图进入 results。共享状态实际是 layout 实例级，不是全局单例；恢复元数据实际在 `sessionStorage`，不是登录凭证。已有项目上下文与请求序列隔离值得复用（E7—E9）。

**方向：先让账号生命周期拥有工作台状态，再集中当前创作投影，最后替换四个必经页面。**

- **职责与 seam：**已核验账号上下文与业务呈现之间是 seam；interface 让调用者消费当前创作状态、历史预览和真实可执行动作，不要求各自拼 S00—S12、审批与任务规则。
- **implementation：**U1/U2/U3 是现有内部状态的投影，不是替换。U3 只由当前 revision 的已发布且可访问交付成立；当前 U1 同时预览旧版本是合法状态。历史选择不修改确认或触发模型。
- **账号隔离：**把现有项目 context / sequence 扩为包含账号身份生命周期版本；同一账号重新登录也换生命周期，成功、错误和结束回调都要匹配。abort 不是隔离证明，也不等于撤销已受理任务。
- **清理与恢复：**退出、切号及其他标签页身份变化一起清除列表、草稿、查询缓存、勾选和临时图片 URL。恢复元数据按稳定账号与项目关联；无账号的旧键不自动认领。重新登录只查询原意图，不重放生成。
- **adapter：**保留现有 fetch transport 与测试 HTTP 替身；存储／身份通知留在 implementation 内。登录秘密不进入浏览器可读持久存储，界面状态与服务端会话分开。
- **depth / locality / leverage：**布局、需求卡、输入、预览与恢复入口共享一套投影；会话失效与修订规则有 locality，同一 interface 测试取得 leverage。
- **deletion test：**`useWorkflow` 自身已有取消、序列和冲突刷新行为，不是可随意删掉的 shallow module。R3 应吸收分散规则；若删除 R3 仅少一次转发、页面仍各算状态，就没有深化。

**文件范围：**`src/composables/useWorkspace.ts`、`useWorkflow.ts`、`api/client.ts`、`router/index.ts`、`layouts/WorkspaceLayout.vue`、`components/workflow/WorkflowPanel.vue`、旧阶段页及新增认证呈现。前端路径均位于 `main/`；测试继续放仓库根 `tests/`。

**验收：**A→B→A、同账号重新登录、跨标签页、历史返回及晚到成功／错误均不串数据；当前 U1＋旧图预览、发布／撤销、手机布局均正确；导航、刷新、重新登录不增加模型调用。对应 `V3-AC-13—15、22—29、38—39`。

## 迁移顺序与完成条件

下表是候选被选择、详设确认后的执行次序，不是本轮已实施清单。

| 阶段 | 执行动作 | 完成条件 |
|---|---|---|
| P0 来源与回退点 | 从实际启动配置、挂载和运行实例解析数据根、数据库、WAL 与引用文件；验证完整备份；冲突来源由维护者明确选择 | 有唯一来源清单、已验证可恢复副本和回退点；没有修改原数据来“试探”来源；未认领内容仍隔离 |
| P1 账号与归属（R1） | 新增账号／服务端会话、初始化／恢复、审计与所有者迁移；接通全部业务出口；分离个人安全视图与管理诊断 | 权限矩阵全覆盖；认领幂等且不伪造历史操作者／批准；会话、密码、CSRF、限流及审计故障符合 SRS；业务默认拒绝 |
| P2 原子受理（R2） | 先明确意图／执行尝试，组合确认事务；S07／S08 关联同意图；持久化计数、占用和恢复结算 | 并发／受理后失败／崩溃的状态与计数一致；新生成须显式授权，查询与原任务恢复不新提交 |
| P3 浏览器生命周期（R3 前半） | 在原布局中先加入账号隔离、会话失效收敛及恢复元数据归属 | 切号、退出、跨标签页和晚到响应测试通过；旧项目级回归不退化 |
| P4 连续工作台（R3 后半） | 收拢三状态投影，替换四个必经页面，连接已确认的单次受理动作 | 当前版本／历史图不混淆；桌面双列／手机单列可操作；单次主操作不靠浏览器串联旧动作冒充 |
| P5 局域网发布门槛 | HTTPS 同源、Host／Origin／可信代理、CSP、资源 no-store、周期备份与受控恢复全部落地 | SRS 第 13 节逐项有证据；真实手机／桌面无证书警告；恢复撤销会话和链接、执行到期并保守处理受理账本缺口 |

P0 的一次性备份先于任何迁移；P5 的周期备份与恢复是正式运行条件。开发和测试可在隔离回环环境推进，完成 P5 前不扩大为局域网正式账号入口。

## 验证方法

1. **同一 interface 测行为。** HTTP 入口和真实临时 SQLite 是权限／受理测试面；供应商用已有 adapter stub，断言调用次数、顺序及门禁。保留文件缺失、撤销、旧资产和原子发布测试，不用逐个私有 helper mock 代替它们。
2. **故障与竞争。** 受控时钟覆盖会话、链接、滚动窗口、保留期和备份；事务回滚、审计失败、并发连接、进程强杀和恢复覆盖计数／占用；数据库不可用与归属不可证时安全失败。
3. **浏览器与运维。** jsdom 回归之外，用真实浏览器验证 HTTPS、Cookie、CSRF、跨标签页、缓存及 320／768／1440 CSS 像素；在独立临时数据根恢复备份，验证业务和文件依赖，不触碰唯一生产副本。

每条 `V3-AC-*` 指向具体自动化或人工证据；本方案的候选验收索引是导航，不替代 SRS 全部验收。精确旧测试锚点和本次实际执行结果见证据索引。

## 保留项与范围护栏

- 保留真实供应商 adapter／测试 stub、SQLite 短写事务、数据库唯一约束、只读恢复与原子发布。它们已经隐藏复杂度，不为目录整齐而删除。
- v3 必需但非纯重构的工作必须单列：账号／会话／凭证、审计、额度记录、HTTPS、备份与所有者迁移。不能把“重构完成”写成“这些功能已安全交付”。
- 不引入微服务、Redis／队列、通用工作流框架、全量事件溯源、团队租户或支付；不重写全部 stage。单台本地实例的现有依赖尚无证据需要这些投入。
- 不仅为行数拆 `useWorkspace`、不机械拆所有 Python 文件、不为单一 implementation 预建第二套 adapter。**删除后复杂度是否回流到调用者**才决定 depth。
- 库、运行依赖及有限资源预算在所选候选的详设中固定：登录／凭证限流默认值与存储、口令长度上限及哈希并发预算、请求体上限、时间窗口边界、未知占用结案规则、备份一致性过程。缺少这些决定不进入正式交付；不重新询问已经确认的产品范围。
- 文档、报告、脚手架与测试放 `main/` 外；本次不移动后端目录、不合并两个布局、不修改现有未提交打包调整。后续布局变更另行证明 import、迁移、配置与数据根一致。

用户选择 R1／R2／R3 后，只展开所选候选的约束、替代 interface 与可存活测试；先完成选择再冻结设计。确认的长期决策届时记录 ADR，澄清的领域术语进入仓库唯一领域词汇来源，未选方案不伪装成既定架构。
