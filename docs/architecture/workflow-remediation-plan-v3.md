- **文件归属：**业务实现放 `main/` 对应模块；测试放 `backend/tests/`、`tests/`；证据放 `docs/acceptance/`；临时探针与截图放 `main/` 外。沿既有后端依赖和迁移入口修改，不在本批搬迁两个布局或处理真实数据根。

## 2. 修改批次

下文后端入口相对 `main/backend/app/`，前端入口相对 `main/src/`；测试入口相对验证表标明的目录。

每批先建立对应用户行为的失败回归，再改实现；私有 helper 探针只辅助定位。测试在临时 SQLite 和可计数适配器替身上验证真实 HTTP／工作流入口、批准与资源可见性。完成记录写入独立验收文件，原设计文档保留规范身份。

### P0：固定基线与受影响门槛

1. 记录 HEAD、分支、`git status`、本批涉及文件差异和规则／契约版本，保留用户未提交修改；外部更新后重读受影响路径。
2. 将 F1—F5、H1 与新前端缺口分别标为“仍复现／已变更待验／已有当前证据／未知”，记录最小场景与测试入口。
3. 对照当前 R1／R2／R3／Release 验收记录，确认哪些覆盖本批代码和新要求；记录不可复用的旧证据及暂未具备的环境。

**结束条件：**每个发现都有当前证据层级、归属批次和验收 ID；前置门槛缺失有明确阻塞范围；没有把旧记录、探针通过或文档更新当作阶段完成。

### P1：收敛服务端裁决，先补免审再消除误拦

**主责：**R1 内容放行边界；R2 正常与恢复接入。
**现有入口：**`workflow/contracts.py`、`prompts.py`、`state.py`，`stages/s01.py`—`s05.py`、`s07.py`、`s09.py`—`s12.py`；按实际审查调用清单确定修改范围。

1. 在现有 workflow 边界内建立小型规则目录和统一裁决函数：输入目标、规则版本、服务端适用性、合法证据及模型结果，返回可记录的有效裁决或类型化问题。新增文件名由实现确定，不引入通用规则引擎。
2. 先映射全部现有必审 ID 与允许的重复实例语义，再逐阶段替换分散校验；所有正常／S12／历史审查消费者逐一登记为复用或明确兼容。支持建议不等于接受任意规则名正则。
3. 同时对齐 reviewer 输入、提示词和契约：总裁决 pass 且适用阻断项全 pass 时，已登记建议可给负面反馈；总裁决与必审证据矛盾仍为协议问题，真实安全发现映射到阻断规则，不被 advisory 吞掉。
4. 保持原有目标摘要、依赖、批准有效性和对外内容控制。记录规则版本，重复实例逐条检查，失败不被后一个 pass 覆盖。

**结束条件：**WG3-AC-01—03、12 在正常与恢复入口有红→绿证据；N/A／缺项／空证据／陌生规则／非法证据／重复中失败均有反例；已登记建议四种结果均有对照。受影响 R1 出口不泄露候选或未批准图，补证完成后才进入 R2 修复批次。

### P2：原意图内修编制，不强迫用户重改需求

**主责：**R2。
**现有入口：**`stages/s07.py`、`s12.py`、`roles.py`、`state.py`，以及 `generation_cycle.py`、`generation_guard.py`、`services/recovery.py` 中实际持有意图／提交事实的接口。

1. 以类型化原因替代文案子串，区分缺信息、可修复编制、真实漂移、拒绝、缺证据、协议问题、技术故障与远端未知；显示文案不决定状态转移。
2. 原意图修复检查授权、账号状态、确认摘要、依赖和未提交证明；定向重编制后重审。预算在候选产生前持久化扣占，正常、失败和 S12 共用，刷新／重启不重置。
3. 技术故障停止自动调用，后续由真实可用的手动恢复动作继续；已提交／提交未知走原任务核实，图片提交不藏进文本修复。需求实质变化才进入新版本与重新确认，计数和槽位按原受理事实结算。
4. 保留 H1 的正例；补准确文案、数值、否定、数量、缺字和跨无关句拼字的反例。文本覆盖与独立语义检查相互补充，不用字符子序列充当内容合格证明。

**结束条件：**WG3-AC-07—09 通过；HTTP 场景中原快照、intent、计数保持正确，预算耗尽即停。技术超时、账号禁用、崩溃恢复、远端未知及并发恢复均验证调用次数；对同一授权不会重复提交图片。

### P3：一次确认绑定完整快照和约束强度

**主责：**R2；回归 R1 内容与历史出口。
**现有入口：**`contracts.py`、`stages/s03.py`—`s07.py`、`s09.py`，`workflow/tables.py`、`state.py`、`prompts.py` 与批准／交付展示读取处。

1. 先列批准需求、创意和视觉字段→执行快照→S07→S09→历史展示的映射，覆盖背景、配色、文字布局、参考处理、保留规则等全部字段；非执行项给出明确去向。
2. 在新契约中表达稳定约束 ID、字段值、来源、hard／soft、用户锁定依据、快照及规则版本。这是待实现逻辑模型，不宣称已有 API／数据库字段；冻结编码和摘要规则后同步生产者、审查者、投影及消费者。
3. 卡片摘要绑定同一快照及强度；S07 覆盖全部确认内容，S09 只以适用硬项决定图片合格。模型建议不通过写入 `preservation_rules` 自动变硬；用户明确必须／禁止项也不被静默降软。
4. 版本化处理旧卡片、批准和恢复检查点：完整识别且可兼容才读取，缺少新强度／字段依据的旧版本保持原语义；新契约进入新需求版本并重确认，旧摘要和历史批准不回写。若新增持久化字段，沿现有迁移链提供临时库升级及失败演练。

**结束条件：**WG3-AC-04—06、12 通过；仅填专用字段仍可在编制请求和质检上下文找到同值与来源；软偏好未知／用户锁定硬项未知构成一过一挡对照。强度改变使旧批准失效，历史仍用原快照。P1—P3 合并后的 R1／R2 影响面、原子受理、额度和不重发回归通过，才进入 R3。

**现有入口：**`workflow/schemas_workflow.py`、`dispatch.py`、`presenters.py`、`services/projects.py`、`routers/projects.py`、`schemas.py`；前端 `api/client.ts`、`api/workflow.ts` 与 `api/types.ts`。

2. 本人项目标题搜索在所有者过滤、标题条件之后分页；查询与游标绑定，空查询、切换查询、游标不匹配和空结果有确定行为。列表状态来自当前任务事实，不借旧成功图标记当前完成。

**结束条件：**WG3-AC-10 的服务端部分、FE3-AC-10 与新出口权限矩阵通过；正常／恢复投影语义相同；搜索能命中未加载页的本人项目，他人项目不可见，重命名无模型调用且需求摘要未变。契约证明后再制作依赖它的 UI。

**主责：**各阶段影响面与 V3-Release。

1. 将门禁 WG3-AC-01—12、前端 FE3-AC-01—15 与 SRS 对应项逐条写入验收矩阵；每项记录基线、步骤／命令、预算、模型／图片调用次数、受理计数、UI 与资源结果及残余未知。部分通过只关闭对应项。
2. 验证完整链：明确发送→审查→确认受理→可修复编制→单次提交→报告／图片独立批准→交付清单→原子发布→只读成果→回原对话修改。另跑硬失败、证据未知、技术中断和旧历史路径，未放行图始终无预览／下载。
3. 在独立数据根验证快照／规则版本兼容和备份恢复。回滚先停止新受理，保全已提交／未知任务的账本与核实能力；代码只回到能解释现存快照／检查点的兼容版本。禁止直接恢复旧库以清掉受理计数，禁止恢复已证实的免审漏洞；需要不兼容回滚时保持维护隔离并另行制定数据处置。
4. 运行进程、静态构建和发布包分别确认版本。真实供应商及真实设备按既有发布程序另行授权取证；模拟测试不代签外部环境，满足 HLD／Release 门槛后才扩大正式运行入口。

**结束条件：**验收矩阵无未归属项；所有本次必测项及被影响的既有门槛均有当前证据；不兼容、权限、计数、图片发布与未知结果路径无遗留失败。缺少真实设备／发布环境证据时，只报告已完成的层级，保持对应发布条件未通过。
