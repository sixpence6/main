# 四角色协作与门禁移除审查（2026-11-10）

本次需求：取消创作流程的业务审查与逐阶段确认，保留四个角色协作，用户对话不用固定报告格式。本文替代旧设计里关于默认新流程的审查／确认停点描述。历史协议保留用于已有数据读取和回归验证；不能把历史实现仍存在等同于当前流程仍执行它。

## 钢笔故障的实证

只读检查了本地保存的这次钢笔对话及对应调用，不修改原库。模型在北京时间 2026-11-10 12:14:53 和 12:15:21 返回成功：`status=ready`、`texts=["商务钢笔 黑色金属笔夹"]`、`must_preserve=[]`、`unresolved=[]`。流程却记录为 S03／failed／SERVICE_UNAVAILABLE。

将同一份保存结果交给旧需求校验，仅切换 `text_authorized`：

```text
从保存的用户消息计算文字授权：False
同一份需求，text_authorized=False：SERVICE_UNAVAILABLE
同一份需求，text_authorized=True ：PASS
```

旧 `_text_authorized` 只查用户消息中的“文字／文案／标题”等字眼，不理解 `2B` 对应的选项，也不把随后回答的文字原文与问题绑定。这使已经正确抽取的需求被本地检查拒绝，再被包装成服务故障。现有数据库记录不支持“供应商宕机”这一解释。

另有两个可直接核查的问题：旧报告把没有特殊保留要求的空数组继续显示成“待补充”；报告要求用户用 `1A 2B` 回复，但展示的示例未必有明确字母 ID，导致回答依赖模型猜对应关系。

| 故障恢复 | 保留输入与任务身份；需求／视觉恢复使用当前协作指令，不重放旧门禁提示词 |

四个角色分别是需求助手、参考图分析师、视觉策划师、生成工程师。有参考图时四个角色参与；没有参考图时无需调用参考图分析师。生图 API 调用、文件处理和交付由程序执行，不另外增加角色。完整文字需求通常调用三次模型；已绑定参考图的路径通常调用四次。聊天首次附件还包含识图前的消息归因，识图后会重新调用需求助手整合报告，因此可能多一次需求调用，仍只有上述四种岗位。调用次数不作为用户流程门禁。

默认 `WORKFLOW_ROLE_POLICY=collaborative`。该模式固定关闭业务审查，不受旧 `WORKFLOW_GATE_MODE=strict` 覆盖。`legacy` 和 `consolidated` 仅用于历史协议兼容与相应回归测试。当前配置也适用于旧任务继续，不要求新建生成意图。

对话自然语言与内部传输协议分开：模型的 `reply` 用于用户交流；内部 JSON 字段仍用于角色交接和图片 API 请求，不作为用户必须填写或阅读的格式。

## 仍存在的执行条件

## 扩展行为审查后的修复

工作区另一份 [行为审查](../reviews/backend-generation-flow-20261110.md) 记录了四个当前协作路径缺陷。已执行其原始探针复现，并完成以下修改：

1. 首次附件的前置消息归因结果不再直接作为识图后的需求稿。识图完成后，需求助手读取真实报告再整合，避免已有图片却继续追问商品主体。
2. 完成后收到修改／再生成请求，会创建新的需求版本并继续协作，不再仅回复收到；原交付版本和旧图片记录保留。
3. 当前模式对变更需求／参考图重新策划；附件替换创建新版本，并取消识图后重复启动需求工序，避免旧视觉依赖与新参考图冲突及重复生成。
4. 已要求但未提供的文字原文，作为待回答问题跨轮保留；用户只补主体时继续保留文案问题，提供原文或明确取消后才解决。取消文字也不会被当作要画进图片的字。

原始行为探针 10 项与原有当前链路回归 8 项合并执行：**18 passed**。已将这 10 项收敛到正式回归文件 `backend/tests/test_collaborative_revisions.py`，加入 `npm run check`。原 `audit_*.py` 与审查报告保留为历史复现证据。

最终验证：扩展行为修复后再次执行 `npm run check`，**228 项前端、145 项后端全部通过**；18 项当前协作行为用例已包含在其中。未重建运行容器，未对原库执行迁移。
