# 对话对齐 P1：结果反馈、修改目标与参考图用途

日期：2026-11-10（Asia/Shanghai）。状态：用户已确认规格与测试边界，已发布为 [GitHub issue #155](https://github.com/sixpence6/main/issues/155)，标签 ready-for-agent；尚未实施或验收。

## Problem Statement

用户已经能通过 P0 的引导把模糊想法变成可确认的提示词，但看到图片后仍可能只能说“太乱了”“不够高级”。如果助手猜错不满意的原因，或者把历史图片、参考图和当前结果混在一起，用户需要反复解释，还可能失去原本满意的商品、文案和画面要求。

当前已有新版本生成、历史结果与提示词保存、需求累计和生成期间的后续意见记录。现有新版本入口以当前交付为起点，尚不能据此认定已经完成多图指代、历史修改目标绑定和完整的反馈归因。

## Solution

在同一个聊天中，让用户选清要改的图片，用一句日常表达指出不满意，助手把反馈整理成一个主要调整方向，并说明“本轮改什么、保留什么”。明确修改直接准备新提示词；模糊评价先问一个有区分度的问题。每次执行仍展示完整、可编辑的正向和反向提示词，等待用户点击“确认使用以上提示词生成”。

参考图用途通过对话表达：这是我的商品、只参考布局、只参考氛围。用户不必理解内部字段，也不必填写新表单。修改以新版本交付；无法保证局部编辑时，明确说明会按调整后的要求重新生成。

## User Stories

1. 作为创作者，我希望说“产品太小”就能准备突出产品的修改方案，以便不必描述专业构图参数。
2. 作为创作者，我希望说“太乱了”时得到减少道具、扩大留白等具体解释，以便判断助手理解是否正确。
3. 作为创作者，我希望说“不够高级”时得到差异清楚的方向，以便避免反复收到同一种画面。
4. 作为创作者，我希望说“不好看”后只回答一个主要问题，以便快速定位偏差。
5. 作为创作者，我希望明确说“去掉文字重新做”后直接看到新提示词，以便不重复回答用途和风格。
6. 作为创作者，我希望明确说“只换背景”时商品、文案和禁止项继续保留，以便修改范围可控。
7. 作为创作者，我希望“B，但别那么暗”同时保留 B 的方向与亮度补充，以便自由表达不被选项吞掉。
8. 作为创作者，我希望可以说“你帮我选”，以便助手在本轮修改范围内提出推荐。
9. 作为创作者，我希望可以拒绝全部方向，以便助手更换调整思路而非重复换措辞。
10. 作为创作者，我希望看到简短的改动与保留项复述，以便及时纠正误解。
11. 作为创作者，我希望多张图片中的“这张”不明确时先选目标，以便不会改错图片。
12. 作为创作者，我希望能明确以自己可访问的历史版本为修改基准，以便保留旧图里满意的方向。
13. 作为创作者，我希望只查看历史图或展开旧提示词时不改变修改目标，以便放心比较版本。
14. 作为创作者，我希望发送前看到已选择的目标版本，并能取消选择，以便清楚本轮针对哪张图。
15. 作为创作者，我希望基于旧图修改也生成顺序递增的新版本，以便历史清晰、原图仍可访问。
16. 作为创作者，我希望跨版本没有明确说明的商品和文字变化先得到核对，以便不会误带入另一版本的内容。
17. 作为创作者，我希望说“这是我的产品，只参考另一张的布局”时助手区分图片作用，以便商品不会被示例替换。
18. 作为创作者，我希望已经说明的参考图用途被记住，以便不重复选择。
19. 作为创作者，我希望参考图身份不明时只回答必要的问题，以便不被迫填写固定表单。
20. 作为创作者，我希望更换商品图后沿用无关的审美选择，并重新核对依赖旧图的观察，以便上下文既连续又可靠。
21. 作为创作者，我希望助手承认看不清的品牌、材质和细节，以便不会把猜测当成商品事实。
22. 作为创作者，我希望生成中输入的修改意见被保存，以便本次任务结束后还能继续调整。
23. 作为创作者，我希望结果状态未知时不会因继续聊天再提交一张，以便避免重复生成。
24. 作为创作者，我希望“先讨论”“先别做”只保留交流，以便不会误触发准备或执行。
25. 作为创作者，我希望每个新版本都重新确认当前完整提示词，以便没有一次图片调用超出我的授权。
26. 作为创作者，我希望刷新、切换会话后恢复同一目标和待答问题，以便不中断修改。
27. 作为创作者，我希望过期选项或旧提示词被拒绝并给出当前状态，以便旧操作不会覆盖新决定。
28. 作为创作者，我希望无法做局部无损编辑时提前知道会重新生成，以便对结果变化有合理预期。

## Implementation Decisions

- **沿用现有架构。** 四角色继续传递并保存原始 Markdown；反馈目标、来源、版本和可操作问题由程序维护。复用现有需求累计、消息受理、工作流投影、生成意图、提示词准备与最终确认，不增加工作流阶段、审核角色或第二套状态机。不恢复旧逐阶段业务确认或内容审查流程。
- **修改目标是独立的领域事实。** 保存项目、目标运行、已发布交付、生成记录、图片资产、目标需求版本、发起消息和本次需求版本的关联。绑定同时带来目标版本的需求及其原始交接文档，不能从“最近的一份文档”推断旧图上下文。图片和历史提示词必须属于同一可访问快照。
- **公开消息契约向后兼容扩展。** 文本消息可附带可选的修改目标标识；服务端负责解析为上述完整绑定并验证归属、可访问性、交付状态和当前版本。无目标的旧请求保持现有行为；明显指向多个版本的文本进入目标澄清。请求继续携带现有 expected_revision 与 request_id；异参重放、过期版本和失效目标不能落入默认最新图。
- **目标选择先于修改受理。** 聊天结果旁的“以此图调整”只将版本引用加入唯一输入框的草稿，可取消；发送后才保存本轮目标与修改请求。浏览、下载、展开历史提示词本身均无业务写入。刷新已发送的待答状态从服务端恢复，草稿按已有账号与会话隔离规则处理。
- **默认与歧义规则。** 没有旧版本指代且当前只有一个明确结果时可使用当前图；“第一张”“版本 2”需唯一匹配；多图“这张”、不存在或不可访问的目标先澄清或报告不可用。新上传图不能静默变成历史修改目标。跨项目或跨账号目标一律拒绝，不暴露其内容。
- **历史修改仍为线性新版本。** 显式选择历史版本后，以该版本为基准加本轮用户增量，创建项目下顺序递增的新版本，并记录来源版本；不复活旧运行、不覆盖旧交付、不建设分叉树。与当前项目不同的商品、文案或参考依赖若存在实际冲突，先用一个问题核对；不能把当前最新内容和旧图需求无来源混合。
- **反馈归因采用渐进对话。** “产品太小”“去掉文字”属于明确调整；“太乱了”可提出减少道具、扩大留白等主要方向；“不够高级”“不好看”在无法唯一判断时提出一个主问题，最多三个选项并保留自由输入。复用 P0 的探索预算、已回答主题和硬问题规则，不为改图另加一轮固定问卷。主观评价不自动等同于事实错误，也不自动授权图片执行。
- **需求按增量更新。** 继承目标版本未被修改的主体、准确文案、禁止项、用途及参考用途，保存本轮变更和保留项及用户来源。明确移除文字才能清空原文；缺省不能清空。推荐尚未被选择时不能作为用户事实；委托仅涵盖本轮问题。文本、按钮、字母及混合答案使用同一持久化绑定。
- **参考用途维持现有能力边界。** 复用商品／布局／氛围等现有用途语义；明确上传说明直接使用，不清楚且影响主体身份时才问。当前受理流程仍只绑定现有支持数量的有效参考文件；涉及两张图的诉求先解释用途并指出当前能力限制，不暗示已支持多参考文件同时提交。新商品图使依赖旧图的观察失效，用户独立表达的审美选择和文字不随之清空。无法核验的材质、品牌和性能仍是不确定信息。
- **明确本轮实际能力。** “只换背景”解释为此次需求仅调整背景；如果当前适配器只能重新生成，提前说明不保证其他像素不变，不伪装成局部编辑。只读当前配置所支持的尺寸、数量、参考数量和编辑能力，不新增承诺。
- **执行边界不变。** 明确修改请求可以启动有预算的提示词准备；纯反馈讨论、目标待定、硬要求待补和暂停时不执行图片。准备后展示本轮完整可编辑提示词及目标版本；用户最终确认前供应商图片提交为零。提示词改动原样保存为新等待快照，旧确认失效。
- **生成期间反馈不自动排队。** 运行中或远端结果未知时保存消息、当时运行／目标、需求版本及文本，保留已提交快照。状态确定后可提醒用户继续；需用户明确继续本轮修改才准备下一版，再次确认提示词后执行。意见不能因完成、刷新、恢复或查询而自动消费。
- **旧数据与恢复。** 旧运行缺少新绑定时只展示可证的历史信息，不伪造目标或需求来源。无法恢复某个历史目标时报告不可用并保留文本。问题和目标在服务端一并检查新鲜度，晚到的旧运行响应不覆盖当前修改。
- **交付顺序。** 先补目标及来源契约和持久化，再接反馈归因及 Markdown 上下文，最后接入聊天引用与问题呈现。每一步沿现有 v3 的 R1 → R2 → R3 门槛推进；本规格的 P1 不是 v3 架构文档中同名优先级的替代。

## Testing Decisions

- **主要测试边界：现有对外 HTTP 消息／工作流动作接口。** 使用真实临时 SQLite 和资产存储、现有文本及图片适配器替身，贯穿消息、问题、目标、版本、提示词准备、最终确认及历史读取。断言用户看到的内容、持久化后可恢复状态、实际图片请求与调用次数；不以调用某个私有 helper 或匹配模型整段回复作为通过标准。
- **前端为必要的交互补充。** 使用现有聊天组件测试装置模拟真实响应，验证目标引用、唯一输入框、自由输入、按钮等待、过期提示和刷新。再以真实浏览器覆盖桌面及窄屏、键盘操作和历史查看，证明无意写入为零。
- **沿用的测试先例。** 现有“对话引导与需求对齐”测试覆盖 HTTP、临时数据库、问题恢复和供应商计数；“可编辑提示词确认”覆盖确认前零提交及原文编辑；“Markdown 交接”覆盖原文进入下游；“新版本与历史”覆盖原交付可读及版本独立；前端历史和对话选项测试覆盖查看无副作用及版本绑定。复用这些装置，不另建测试框架。

| 验收场景 | 可观察的通过条件 |
| --- | --- |
| “产品太小”“去掉文字重新做” | 不重复无关问题；新提示词反映指定变化，未修改约束仍在；确认前零图片提交 |
| “太乱了”“不够高级”“不好看” | 给一个可理解的主要建议或主问题；最多三个选项；未选建议不写成用户确认 |
| “B，但别那么暗”“都不喜欢”“你来定” | 选择与补充均保留；更换方向或按问题范围委托，不丢商品及原文 |
| 多图“这张” | 目标不明确时等待澄清；无新图片提交，不默认覆盖最新图 |
| 显式选历史版本 | 新版本继承目标版本并记录来源；版本号递增；旧图及其提示词保持原样 |
| 不可访问、已撤销或不存在的目标 | 安全报告不可用，不替换成当前图；跨账号读取和写入均不成立 |
| 只看旧图或展开旧提示词 | 无修改受理、无目标切换、无供应商调用 |
| 替换商品参考图、改参考用途 | 原图观察不再当作新图事实；保留独立用户选择；超出现有参考能力时明确说明 |
| 生成中、远端未知、恢复后 | 意见可读且目标可追踪；已提交快照不变；不自动准备下一版或重复提交 |
| 提示词编辑、重复点击、旧确认 | 保存的编辑等于实际请求正文；同一确认仅一次提交；旧绑定被拒绝 |
| 刷新及旧会话 | 当前目标、问题和待确认提示词一致；缺失历史不会被补造 |

- 实施完成必须从仓库根运行 `npm run check`，并将新增关键回归纳入该入口；涉及版本／恢复迁移时补充完整后端套件。测试与证据留在项目本体目录之外。
- 再用原规划建议的 5—8 位目标用户观察模糊反馈与明确修改各一个任务，记录是否改错目标、是否丢约束、主观符合度与重复提问；人数不构成统计显著性承诺。任何未经最终确认的图片提交、重复提交、越权目标或原文静默改写均阻断本期验收。自动化通过不能代替真实模型和用户观察。

## Out of Scope

- 构图示意、色调预览和跨项目长期偏好，交由 P2。
- 多参考图提交、局部无损编辑、遮罩编辑、任意输出尺寸、批量生图及适配器能力升级。
- 历史分叉树、覆盖旧结果、修改原始交付、自动消费后续意见或自动再生图。
- 新工作流阶段、逐阶段业务审批、通用工作流框架、与本期无关的工作区清理和发布。
