## 1. 改造目标与范围

**目标：用户只与“智能生图助手”对话，完成描述、澄清、查看提示词、确认出图和继续修改。** 原创作界面的布局与交互推倒重建，不把旧工作台缩小、折叠或搬进聊天气泡。

视觉参照：`https://linche-portfolio-29244.app.workbuddy.host/?sharecode=OMYZKE7RWI`。2026-11-03 已实际打开观察：浅灰紫背景、圆角白色侧栏与主面板、左侧会话列表、单一消息流、底部固定图文输入。比例、留白、颜色、圆角、气泡和输入框尽量对齐参考页；使用本产品品牌与业务文案，实现和资源由本项目提供。

| 重建或移除 | 保留与边界 |
|---|---|
| 重建整个创作外壳、侧栏、聊天区和输入区；原布局与旧组件结构不作为保留前提 | 保留后端已有生成、审查与发布能力，按新确认顺序调整必要衔接 |
| 移除需求表单、参考用途下拉框、复杂确认卡、流程/任务面板、阶段导航、技术报告常驻区 | 必要需求确认、参考用途、授权和恢复仍通过对话及轻量动作完成 |
| 移除创作区的独立成果页、对话/成果切换及生成后的自动跳转 | 保留历史项目、图片、批准记录和版本事实；旧入口安全兼容 |
| 移除重复标题、模型状态面板和参考站专属模型选择/思考过程控件 | 登录、账号管理及管理员页面本轮不重做；必要账号、用量与数据使用说明保留为轻量入口 |

文档、测试、截图和临时脚手架放在 `main/` 外。删除范围以旧创作呈现及失去调用者的代码为限，不清空用户数据，不顺手重构无关模块。

## 2. 已确认的界面与对话契约

### 2.1 页面骨架

```text
浅灰紫页面背景
├─ 左侧圆角侧栏
│  ├─ 智能生图助手 / 新建对话
│  ├─ 搜索对话 / 本人历史会话列表
│  └─ 账号及必要信息入口
└─ 圆角白色聊天主面板
   ├─ 顶栏：当前对话标题；窄屏提供侧栏展开按钮
   ├─ 唯一消息流：用户文字与图片 / 助手回复 / 提示词 / 生成图片
   └─ 唯一固定输入区：图文输入 / 上传 / 发送
```

新会话只显示简短欢迎语，例如“发来商品图片，或告诉我你想做什么样的电商图片”，以及原输入框。首次明确发送才创建创作记录，不另设功能卡、统计、流程教程或第二个开始入口。

### 2.2 会话、意图与参考图

- **会话即连续创作。** 侧栏一条记录对应一段完整创作对话，内部包含初始需求、参考图、澄清、图片和修改历史。点击新建才开启另一段对话，每次出图不另建会话。搜索与列表直接位于侧栏；标题搜索和重命名沿用服务端所有者边界，不新增删除项目或本地业务数据库。
- **交流与修改分流。** 问候、解释问题、“先别生成”只产生合适的交流回应，不擅自更新需求、创建需求版本或生成图片。实质修改才更新创作要求；信息足够时直接收敛，只追问阻塞缺项。每句输入都套用同一需求处理动作不算完成对话改造。
- **图文共同发送。** 文件选择、粘贴、拖入均在唯一输入区；发送前可预览、替换或移除附件，发送后图片属于对应用户消息。参考用途通过自然语言表达，不靠独立配置表单；指代不明时助手追问。图片引用必须绑定稳定标识与实际版本，不能仅按当前缩略图推断。实施时核对服务端附件数量与引用能力；不足以承接已确认交互的部分列为缺口，不能在前端假装支持。
- **唯一修改入口。** 需求、参考用途和提示词修改均在底部原输入框提出；不新增提示词编辑器、反馈输入框或隐藏的第二套表单。快捷动作不代替用户明确生成授权。

### 2.3 图片、等待与失败

- **结果内联。** 获准发布且可访问的图片作为新的助手消息出现，提供放大与下载。每轮图片保留在各自消息位置，不用新图覆盖旧图，不自动跳页或滚回其他会话。
- **修改基准明确。** 默认延续当前最新方案。历史图可以回看、放大和下载，查看旧图不改变修改基准、不触发生成，也不隐式增加历史分叉功能。
- **历史真实。** 图片与其需求、实际提示词和交付版本绑定；刷新后从真实记录恢复，不用当前提示词解释旧图。撤销、过期或文件丢失时更新可见状态，不用缓存私图或别的版本兜底。
- **等待轻量。** 正在执行时只保留一条当前任务的简短状态，随真实状态更新，不持续新增进度消息。用户可以写草稿，忙碌期间暂不提交新请求，也不暗中排队。内部阶段、虚构百分比和模型思考过程不进入正文。
- **失败可行动。** 在原对话说明安全原因，仅展示后端真实允许的核实、补充或恢复动作；只读核实与可能调用模型的恢复明确区分。不自动重生成，不把未放行结果称为成功。

### 2.4 输入与可达性

消息区独立滚动，底部输入不遮挡正文。Enter 发送、Shift+Enter 换行，中文输入法选字不触发发送。上滚阅读时新消息不强制拉到底部。小屏把同一侧栏收为单层抽屉，保持同一个聊天主体；键盘焦点、附件操作、放大关闭和软键盘下的发送按钮均须可达。

## 3. 先展示真实提示词，再确认生图

### 3.1 用户可见顺序

```text
明确创作/修改输入 → 必要澄清与需求整理
  → 本轮真实生图提示词编制与独立审查
  → 助手消息中展示完整已批准提示词，停下等待用户
  → 用户点击“确认使用以上提示词生成”
  → 提交图像生成 → 质检、审查与发布 → 图片追加到原对话
```

提示词默认全文展开，支持复制，确认按钮紧随其后。需求摘要可以简短说明上下文，但不能冒充执行提示词。这里的正文是实际传给图像生成模型的提示词；若实际请求包含负向提示词，也一并展示。影响本次生成的参考图与输出要求须可核对，采用简明说明而不是恢复配置面板。

用户在原输入框提出修改后，重新准备、审核并展示新提示词；旧消息可回看和复制，旧按钮不再具有授权能力。仅“好的”“继续”、查看提示词、刷新和重新进入对话均不等同本次生成确认。

### 3.2 执行绑定与安全条件

- **先看后用。** 最终点击之前不得提交图像生成；只有当前有效、已批准提示词可进入待确认状态。未批准候选、内部系统指令、审核自由文本与模型思考过程保持原有隔离。
- **展示即执行。** 服务端将确认绑定到操作者、所属项目、需求版本、提示词版本/摘要、参考依赖与输出参数等不可变执行事实。实际生成必须消费用户看到的同一份提示词；点击后重新编写或切换提示词须重新展示并获得确认。
- **服务端停点。** 已批准提示词展示后持久化等待最终授权，后台驱动不能自行穿透到图像提交。跨标签页、重复点击、丢响应重放或恢复均执行同一有效性校验；前端隐藏按钮不是授权控制。
- **读取无副作用。** 首次加载、刷新、轮询、路由兼容跳转与恢复页面不编制提示词、不隐式授权、不启动生图。准备提示词的模型调用必须归属于明确创作/修改动作；普通交流不自动进入准备链路。

### 3.3 受理、计数与恢复的对齐门槛

本轮将提示词准备放在最终生图确认之前，属于真实流程变化。当前“确认需求即受理，随后自动编制并生图”的路径不能原样保留，也不能通过前端串联旧接口伪装为新契约。

进入实现前，明确并落下可测试的契约：提示词准备的授权与资源预算、持久化待确认状态、最终生图授权绑定、生成意图与用量/槽位账本的对应关系，以及失败/过期/修改后的结算与恢复。既定额度与幂等规则不因增加停点而被绕过，同一逻辑尝试不得因预览和最终确认重复计数；任何确需改变产品计数口径的设计，须单列差异并另行确认，不能由 UI 改造暗中决定。

恢复只按原任务和有效授权推进。尚未获最终提示词确认的任务不能因刷新或进程重启自动生图；已提交或提交事实未知的任务优先核实，不创建第二次提交。

## 4. 当前基线与必须承接的缺口

以下为 2026-11-03 的源码观察，目的是指出实现不能停留在换皮；进入开发时仍需复核当前代码，不当作测试通过证据。

| 当前事实 | 代码入口 | 本轮影响 |
|---|---|---|
| 聊天页把消息、工作流面板和历史预览顺序挂载 | [ChatPage.vue](main/src/pages/ChatPage.vue) | 改成统一对话时间线，不保留旧面板堆叠 |
| 工作流面板承担真实补充、用途选择、确认和生成动作 | [WorkflowPanel.vue](main/src/components/workflow/WorkflowPanel.vue) | 将必要行为迁入对话语义与轻量动作，不能删掉组件就算业务接通 |
| 搜索、列表和重命名在已有项目抽屉内 | [AppSidebar.vue](main/src/components/AppSidebar.vue)、[ProjectDrawer.vue](main/src/components/ProjectDrawer.vue) | 将真实会话列表直接放进侧栏 |
| 已有独立成果视图及聊天中新发布后的自动跳转 | [ResultsPage.vue](main/src/pages/ResultsPage.vue)、[ChatPage.vue](main/src/pages/ChatPage.vue) | 结果改为消息内联，旧成果入口保持只读兼容 |
| 当前确认需求会写入受理事实并启动后续执行 | [s06.py](main/backend/app/workflow/stages/s06.py) | 最终按钮当前绑定需求，不是尚未产生的提示词 |
| 后台自动执行 S07 编制及审查，再进入 S08 提交生图 | [generation_cycle.py](main/backend/app/generation_cycle.py) | 当前缺少已批准提示词之后的用户确认停点 |
| 工作流投影只公开批准后的 `prompt_plan` 正文 | [state.py](main/backend/app/workflow/state.py) | 有安全读取能力，但不能据此宣称已有确认停点 |

**关键结论：当前正常流程在首次确认前没有本轮真实提示词；编制后又会自动继续生图。因此这是前后端共同改造，不是按钮旁漏放一段文本。**
